## 1. מה בוצע בפועל עכשיו — בדיקת עומס מקומית (adapter-level)

**כלי:** סקריפט Node/TypeScript פנימי, `site/scripts/local-load-test.ts`
(`npm run loadtest:local` בתוך `site/`). לא k6/Artillery/כלי חיצוני — כי אין
עדיין endpoint אמיתי ברשת לבדוק מולו; זו סימולציית in-process של הלוגיקה.

**מה נבדק:** `MockPaymentProvider` + `withIdempotency()` תחת עומס מקבילי גבוה,
כולל תמהיל ריאליסטי: כ-15% מה"משתמשים" מדמים דאבל-קליק על כפתור "קנה"
(שתי קריאות בו-זמנית עם אותו idempotencyKey), ותמהיל תוצאות מציאותי
(רוב approved, ואחוזים קטנים של declined/timeout/error).

**קריטריוני הצלחה שהוגדרו מראש:**
- אין קריסה/exception לא-מטופל תחת מקביליות גבוהה.
- מספר קריאות `createCharge` בפועל **לא עולה** על מספר המשתמשים — כלומר
  אין אף חיוב כפול, גם עם דאבל-קליק בו-זמני.
- זמן תגובה סביר גם בתרחיש timeout (לא נתקע ללא הגבלה).

**תוצאה (הרצה עם 3,000 "משתמשים" בו-זמנית):**

```
מריץ בדיקת עומס מקומית: 3000 "משתמשים" בו-זמנית מול mock provider

תוצאות:
  זמן כולל: 5223ms
  בקשות "משתמש" (כולל דאבל-קליק): 3472
  קריאות provider.createCharge בפועל: 3000
  התפלגות תוצאות: {
  declined: 150,
  timeout: 150,
  duplicate_ignored_race: 472,
  error: 151,
  approved: 2549
}

קריטריון הצלחה (adapter-level): אין יותר חיובים בפועל ממספר המשתמשים → ✅ עומד (3000 ≤ 3000)
קריטריון הצלחה: אין קריסה/exception לא-מטופל תחת 3000 מקביליות → ✅ עומד
```

**פרשנות:** 472 מתוך 3,472 הבקשות היו דאבל-קליק שזוהו נכון כ-`duplicate_ignored_race`
ולא יצרו חיוב שני — בדיוק ההתנהגות הנדרשת. מספר החיובים בפועל (3,000) שווה
בדיוק למספר המשתמשים (3,000), לא יותר. אין חיוב כפול אחד גם תחת עומס.

בנוסף רץ `npm run test:payments` — 12 בדיקות תרחיש (approved/declined/timeout/error/
idempotency/webhook לא תקין/refund על חיוב לא מאושר) — **12/12 עברו**. פירוט:
`site/scripts/test-payment-adapter.ts`.

**חשוב להדגיש את המגבלות של הבדיקה הזו (מה היא *לא* מוכיחה):**
- לא בודקת CDN caching, cold starts אמיתיים של Cloudflare Pages Functions,
  latency רשת אמיתי, או Cloudflare KV/Durable Object (ה-idempotency store
  היום הוא Map בזיכרון תהליך יחיד — ראה `docs/ARCHITECTURE.md` §3.5).
- לא בודקת ספק תשלום אמיתי — רק mock.
- 3,000 "בקשות" רצות בתוך תהליך Node יחיד ללא latency רשת אמיתי — לא מייצג
  זמני תגובה אמיתיים תחת עומס אמיתי.

## 2. תוכנית בדיקת העומס המלאה (לביצוע ברגע שיש סביבת פריסה)

### 2.1 מה ייבדק

| # | תרחיש | למה |
|---|---|---|
| 1 | דף המכירה (`/`) תחת 5,000-10,000 בקשות בו-זמנית (spike תוך דקה) | מדמה גל ויראלי אמיתי — הדרישה המפורשת ב-PROJECT-BRIEF.md היא "אלפי כניסות בו-זמנית", לא עשרות. |
| 2 | `/api/checkout/create` תחת 500-2,000 בקשות בו-זמנית | מייצג את החלק שבאמת מגיע לקנייה (שבר קטן מהתנועה הכוללת, אך זה החלק שנוגע בכסף). |
| 3 | תמהיל דאבל-קליק (10-20% מהבקשות שולחות 2 בקשות עם אותו idempotencyKey כמעט בו-זמנית) | תרחיש ריאלי בעומס+מובייל, נדרש מפורשות ב-PROJECT-BRIEF.md. |
| 4 | תמהיל כשלים מוזרק (declined/timeout מלאכותי דרך ה-mock) בו-זמנית עם עומס | לוודא שנתיב כשל לא מאט/שובר את שאר המערכת. |
| 5 | דף מכירה תחת עומס **וגם** צ'קאאוט פעיל בו-זמנית | לוודא בידוד אמיתי — עומס בצד אחד לא פוגע בשני (ראה `docs/ARCHITECTURE.md` §5). |
| 6 | מדידת ביצועים על חיבור מדומה 3G (Chrome DevTools throttling / Lighthouse) | קהל היעד גולש מהטלפון על רשת ישראלית טיפוסית, לא Wi-Fi מהיר. |

### 2.2 איך

- **כלי מומלץ**: k6 (open-source, טוב לסימולציית VUs מדורגת/spike) או Artillery.
  ייבחר בפועל כשיש target אמיתי לירות עליו.
- **דירוג העומס**: לא "flat load" קבוע — ramp-up חד תוך שניות בודדות ל-peak
  ואז ירידה, כדי לדמות גל ויראלי אמיתי ולא תנועה יציבה.
- **סביבה**: מריצים מול deployment אמיתי (preview/staging של Cloudflare Pages),
  לא מול localhost — כדי לתפוס latency CDN/cold start אמיתיים.
- **תשלום**: מריצים תחילה מול `PAYMENT_PROVIDER=mock` (מוכן כבר), ואז חוזרים
  ומריצים תת-סט מול sandbox אמיתי של הספק שנבחר, ברגע שיש מפתחות (BLOCKERS.md #2).

### 2.3 קריטריון הצלחה (לשער 2 המלא)

- **0% שגיאות 5xx** על דף המכירה הסטטי תחת peak load (זה קובץ סטטי מ-CDN —
  אמור להיות טריוויאלי, אבל נבדק ולא מונח).
- **P95 latency** על `/api/checkout/create` מתחת ל-3 שניות תחת peak load
  (סף ראשוני — ניתן לכיול מול תוצאות אמיתיות).
- **0 חיובים כפולים** בפועל אצל ספק התשלום (נבדק גם דרך dashboard הספק, לא
  רק לוגים שלנו) תחת תרחיש דאבל-קליק בעומס.
- **כל הבקשות עם timeout/declined/error מטופלות בבירור** ללקוח (לא נשארות
  תלויות/"מסתובבות" ללא תשובה).
- **Lighthouse mobile score** סביר (יעד ראשוני: Performance ≥ 80) על חיבור 3G
  מדומה לדף המכירה.
- ניטור זמן-אמת של שגיאות תשלום (`docs/ARCHITECTURE.md` §4) **פעיל בפועל**,
  לא רק מתוכנן.

**רק כשכל הסעיפים ב-§2.3 עומדים מול תשתית אמיתית (לא mock מקומי) — שער 2
נחתם.** עד אז, סטטוס השער נשאר **פתוח**, וה-CTA-ים באתר ממשיכים להצביע
ל-`/waitlist` בלבד (נאכף בקוד, לא רק במדיניות).
